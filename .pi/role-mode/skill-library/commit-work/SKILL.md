# Commit work

## Goal

Make commits that are easy to review and safe to ship:

- only intended changes are included
- commits are logically scoped (split when needed)
- commit messages describe what changed and why

## Branch Workflow

- Commit only when the user explicitly asks. This skill does not authorize a push, pull request, release, or deployment.
- Inspect the current branch and worktree. Preserve an existing task worktree and its branch; create a branch only if the task needs one.
- Never commit directly to main/master for feature work.

## Inputs to ask for (if missing)

- Single commit or multiple commits? (If unsure: default to multiple small commits when there are unrelated changes.)
- Follow the repository's `AGENTS.md` commit-message rules and `docs/development/commit-conventions.md` (paths relative to the repository root). Do not ask for a scope list or impose a subject-length limit.

## Workflow (checklist)

1. Inspect the working tree before staging
   - `git status`
   - `git diff` (unstaged)
   - If many changes: `git diff --stat`
2. Decide commit boundaries (split if needed)
   - Split unrelated outcomes, not required implementation, regression tests, and documentation for the same behavior.
   - If changes are mixed in one file, plan to use patch staging.
3. Stage only what belongs in the next commit
   - Prefer patch staging for mixed changes: `git add -p`
   - To unstage a hunk/file: `git restore --staged -p` or `git restore --staged <path>`
4. Review what will actually be committed
   - `git diff --cached`
   - Sanity checks:
     - no secrets or tokens
     - no accidental debug logging
     - no unrelated formatting churn
5. Describe the staged change in 1-2 sentences (before writing the message)
   - "What changed?" + "Why?"
   - If you cannot describe it cleanly, the commit is probably too big or mixed; go back to step 2.
6. Run relevant verification for the intended changes before committing. Follow `AGENTS.md` and `docs/development/testing.md`, use Volta and coordinated commands, and report failures or unavailable checks.
7. Write the commit message
   - Use the English Conventional Commit subject and allowed types in `AGENTS.md`; scopes are optional.
   - Separate an explanatory body from the subject with a blank line. Include the reason or prior failure when the subject is insufficient, rather than an implementation diary.
   - Mark and explain incompatible changes with `!` or `BREAKING CHANGE:`; this does not authorize a compatibility break.
   - Preserve ordinary Git-generated merge/revert messages as described in the commit guide. A squash commit needs its own valid subject; recheck it after editing.
   - Validate a prepared message with `node tools/commit-check.mjs --message-file <path>`. Do not rewrite grandfathered history or install hooks without permission.
   - Omit any tool-specific footer from commit messages (e.g., "Generated by X", "Co-authored-by AI")
   - Prefer an editor for multi-line messages: `git commit -v`

## Commit Message Template

```text
<type>: <summary>

<What changed.>
<Why it changed.>
```

**Notes:**

- Keep the summary English, imperative and specific ("Add", "Fix", "Remove", "Refactor"); add an optional scope when useful
- Avoid implementation minutiae; focus on behavior and intent
- If breaking: use `!` in header and/or add `BREAKING CHANGE:` footer

8. Repeat only for remaining user-authorized changes. Preserve unrelated work; a clean working tree is not a reason to include someone else's edits.

## Deliverable

Provide:

- the final commit message(s)
- a short summary per commit (what/why)
- the commands used to stage/review (at minimum: `git diff --cached`, plus any tests run)
