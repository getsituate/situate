Status:: proposed

Scope:: Device-local ownership, durable provider access and separation from portable conversation content. Product ownership is established by the requirements; this record does not establish an independent security review or platform qualification.

== Product boundary

link:{architecture-repository-root}/requirements/data/requirements/REQ-0015-connect-user-provided-models.md[REQ-0015] selects OpenAI API-key/direct ChatGPT access, distinct Codex device authorization, Anthropic/OpenRouter API keys and custom/local endpoints. Conversational Pi parity is a long-term goal, not MVP acceptance. Classifiers, external credential sources and arbitrary provider extensions are excluded from this integration.

All operational AI settings belong to the combination of workspace and device:

* Connections, names, authentication methods, endpoint addresses and selected access.
* Credentials, refresh ownership, discovery observations and destination-specific HTTP consent.
* Per-connection model defaults, per-model thinking preferences and conversation-specific overrides.

These records persist outside the portable workspace and its histories. Neither official nor custom synchronization transfers them, including reusable API keys. A new device configures access independently; an unconfigured device is not a broken workspace or synchronization error. Reading and editing local content do not require AI setup.

Authentication, renewal and model requests for user-provided access go directly to the chosen provider. Situate services neither store these credentials nor broker their renewal or use. Managed Situate AI remains a separate account entitlement and never silently replaces the chosen access.

link:{architecture-repository-root}/requirements/data/requirements/REQ-0038-copy-portable-workspaces.md[REQ-0038] retains portable content, layout, plugin configuration and histories while excluding operational AI configuration. A device-local association registry identifies the authorized canonical workspace location; copying workspace files does not copy that association or grant another location's credentials.

== Local storage

The link:{architecture-repository-root}/client/crates/situate-core/src/ai_connections.rs[connection store] owns stable connection identities, configuration revisions, selected access and connection-scoped preferences. The device-local registry assigns an opaque link:{architecture-docs-root}/index.adoc#glossary-device-local-workspace-namespace[device-local workspace namespace] to each authorized canonical workspace location. This associates local AI records with that location; it is neither the portable diagnostic workspace identifier nor a runtime authorization handle.

Reopening that location restores its configuration; another device or a copied or moved location starts with ordinary setup, without automatically transferring credentials. No AI namespace or connection manifest is written to the portable workspace.

Secrets use encrypted app-private storage protected by OS-held keys. XChaCha20-Poly1305 authenticates the device-local workspace namespace and complete connection record, including configuration revision and endpoint. A fresh 32-byte key is stored and read back before publishing replacement ciphertext. Previous keys are retired only after durable replacement.

Credential changes are serialized by device-local workspace namespace rather than view visibility. The credential-replacement journal preserves recoverable replacement ciphertext across cross-store failures. Recovery rejects conflicting configuration rather than resurrecting a removed connection or overwriting another destination. A renewal captures and authenticates the exact connection record before dispatch; an already rotated grant must not be discarded merely because its chat was cancelled.

Unknown, corrupt or undecryptable records are errors, not permission to overwrite them. There is no plaintext fallback. The original credential-migration and legacy-session exception applies only to prototype formats verified never to have shipped publicly; their records are not automatically imported or deleted. Published device-local provider configuration and credentials require compatible storage or a tested, recoverable migration on app upgrade. This does not transfer credentials between devices or into portable workspaces.

[cols="1,3",options="header"]
|===
|Platform |Local protection and qualification boundary
|macOS |Non-synchronizing Keychain items. Production signing, upgrades and locked-store behavior require qualification.
|iOS |Non-synchronizing `AfterFirstUnlockThisDeviceOnly` Keychain items; ciphertext uses first-unlock protection and backup exclusion. Simulator evidence does not qualify physical-device or production-signing behavior.
|Windows |Current-user Credential Manager generic credentials with local-computer persistence. Native runtime and profile/backup behavior require qualification.
|Android |Keystore keys protect wrapping-key records with AES-GCM in app-private no-backup storage. Emulator evidence does not establish physical hardware protection or backup behavior.
|Linux |Secret Service with explicit absent-service, locked-collection and duplicate-item handling. Hardware and per-application isolation are not universal guarantees.
|===

Ordinary reopening and renewal use the authorized OS session without a separate Situate password or routine biometric confirmation. OS lock, first unlock, denial and key loss can still require interaction. A compromised application process or other code with equivalent privileges is outside this boundary's isolation guarantees.

The native provider plugin rejects JavaScript invocation of wrapping-key and authentication-browser operations. UI collects user-entered secrets transiently but does not receive renewed grants or secret request headers in normal status/events.

== Connection and request ownership

Multiple accounts of the same provider have independent IDs and credentials. Names identify them to the user but are not authentication identities. Renaming must not reconnect or rotate access. Adding a connection does not replace an existing selection; removing the selected connection clears it rather than selecting another account.

Resolve a conversation's local connection override before loading credentials. Without an override it inherits the workspace's selected connection on this device. Changing that default does not rebind an explicit conversation selection. Forgetting or removing its connection blocks subsequent use while retaining the draft and choice for explicit recovery.

New connection defaults retain Recommended as a preference. Resolution uses an explicitly ranked catalog filtered for the connection, authentication method and required capabilities. Account-filtered lists, provider observations, static compatibility and unknown discovery are distinct evidence. A listed model is not an entitlement or credit check. No billable request is made to choose a default; discovery failures and catalog updates do not replace explicit choices.

Model and thinking changes are independent of response persistence. A confirmed selection affects the next request; a running request keeps its captured connection, model and thinking level. An uncertain save blocks new submission until readback or retry establishes the stored choice. Completing or stopping a response does not settle a pending preference save.

Conversation contents, tool results and required interruption state remain portable. Operational preferences and per-message provider/model attribution do not. The original Pi integration adapted SDK messages at the execution boundary rather than using them as the portable storage contract. link:{architecture-docs-root}/09-architecture-decisions/ADR-0013-native-conversation-execution.adoc[ADR-0013] replaces that integration with native Rig execution and a Situate-owned conversation format. Continuing synchronized content uses the destination device's own selection.

Native session-generation tokens enforce the link:{architecture-docs-root}/index.adoc#glossary-runtime-workspace-binding[runtime workspace binding]: authorization belongs to the initiating open workspace session and window. Returning from the browser is not authentication success. Closing and reopening the same workspace invalidates an old attempt. Mobile switching can leave the originating workspace open, but continuation still requires its original link:{architecture-docs-root}/index.adoc#glossary-workspace-operation-lease[workspace operation lease] and session authority. This lease retains the workspace operation through completion and cleanup; it is not the plugin worker lease used to drain independent host requests before activation.

== Authentication and transport

Direct ChatGPT and Codex grants, destinations and account bindings are distinct; neither substitutes for the other. Signed identity verification, callback correlation, polling expiry, cancellation and durable renewal remain native responsibilities.

Each device signs in independently where the provider supports it. Device-local storage alone does not prove simultaneous-session support. A method known to displace another device's session must explain that limitation before authentication and cannot offer takeover as ordinary independent-device setup. Do not copy a rotating refresh token for concurrent renewal.

Known restrictions require the method-specific warning, source, consequences and explicit own-risk acknowledgement defined by REQ-0015. Acknowledgement does not grant provider permission or override technical denial. Fictional workshop restrictions are not provider policy evidence.

Custom HTTP requires consent for the exact normalized destination before transmission. Changing the destination invalidates consent. This permission does not authorize insecure redirects, credential forwarding or a TLS certificate-validation bypass. HTTPS retains normal validation.

== Content synchronization and recovery

link:{architecture-repository-root}/requirements/data/requirements/REQ-0013-synchronization-service.md[REQ-0013] assigns end-to-end encryption, authorized-device provisioning and account recovery to official content synchronization. One user-held account recovery key covers officially synchronized workspaces; account login or the operator alone cannot decrypt them.

That recovery boundary does not provision external provider credentials or operational AI settings. Changing a content transport, authorizing a sync device or recovering content must not change a device's local AI configuration. Provider sign-in, provider device-code approval and synchronization-device authorization are separate operations.

Content recovery protocols, key hierarchy, rotation and historical-key custody remain separate design work. The local provider envelope format is not a synchronization or recovery protocol.

== Alternatives

[cols="1,2",options="header"]
|===
|Alternative |Disposition
|Portable non-secret connection configuration with local secrets |Would transfer endpoints and future model choices, contrary to the accepted device-local boundary.
|Encrypted provider credential provisioning through official sync |Encryption does not solve independent rotating sessions and does not match the requirement to configure each device separately.
|Process-global Pi authentication storage |Does not provide workspace isolation or native credential custody.
|Universal portable vault or additional unlock password |Not required for local AI access and introduces unrelated recovery and routine-unlock interactions.
|Server credential or token-renewal broker |Excluded for user-provided provider access.
|===

== Unresolved security rationale

The storage description specifies the encryption envelope, fresh-key replacement and credential-replacement journal, but does not record a comparative rationale for those mechanisms. The link:{architecture-docs-root}/../development/provider-qualification.md[qualification record] describes their implementation and fixture evidence, not why they were selected over other storage designs.
The security rationale and storage-alternative evaluation remain unresolved. Implementation evidence does not establish an independent security review or change this record's proposed status.

== Verification and release boundaries

Verify independent workspace/device stores, copied identities, reopening, multiple accounts, default/override resolution, save/readback uncertainty, cancelled renewal and stale callbacks. Check serialized workspace content for endpoints, credentials, operational preferences and provider/model attribution. Use synthetic credentials and provider fixtures.

A complete journey includes setup, durable save, model resolution, request, reopen, renewal and removal on every claimed platform. Browser fixtures cannot establish native secure-store behavior or actual provider acceptance. Mobile suspension, OS permissions, production signing, backup behavior and independent provider sessions require separate evidence.

The link:{architecture-docs-root}/../development/provider-qualification.md[qualification record] separates source, deterministic fixtures, simulator/emulator components and remaining live/platform gaps. Partial releases must identify unresolved required methods and platforms; neither source coverage nor a host test pass establishes the complete MVP.
