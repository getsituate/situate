Catalog priority `must` applies to the linked requirements; it does not rank them against one another or establish their implementation status.

The current-client scenarios describe safeguards and their verification boundaries, not complete implementation of the target architecture or a passing result for a particular revision.
Data preservation, workspace independence and explicit failure reporting take precedence over silently completing an unsafe operation.
Engineering checks are listed separately from product outcomes.

==== Verification policy

The repository uses one link:{architecture-repository-root}/tools/test.mjs[test runner] for unit, integration, browser, native and static checks.
Quick checks provide local feedback; the default MVP suite covers additional boundaries and dependencies on its selected host.
Expensive extended checks and deferred product platforms are not implied by an MVP pass.
Missing tools or services are reported as failures rather than silently omitted from a selected suite.
Formatting checks are read-only; applying formatting is a separate developer action.
Tool versions are pinned so local and CI results can be compared against known inputs.
See link:{architecture-docs-root}/development/testing.md[the test suite guide] for commands, platform coverage and CI triggers.

Coverage reports show which instrumented source was executed by tests, not whether all relevant outcomes were asserted.
Pull-request feedback compares coverage with a measured `main` revision and identifies both revisions.
An unavailable baseline must be shown as unavailable, not as zero coverage; a decrease informs review without imposing a universal percentage gate.
Test failures remain failures independently of the coverage percentage.

macOS and iOS are the active MVP targets; Android development and verification are deferred.
Automated iOS device verification is not currently provisioned, and the retained mobile workflow is disabled.
Native iOS checks remain explicit development and release work; macOS, browser and workflow-contract checks do not establish iOS qualification.
See link:{architecture-docs-root}/development/testing.md#mobile-ci-disabled[mobile CI limitations] and link:{architecture-docs-root}/development/testing.md#native-ios-application-journey[the explicit iOS application journey].
