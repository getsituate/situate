# Workspace AI design scenarios

The [design workshop](design-workshop.md) contains synthetic AI-access and chat-model scenarios under **AI access**, **Chat** and **Settings**. Choose **Connect an AI provider**, **Conversation** or **AI settings**, then select a **Starting state**. For the post-creation offer, use `ai-offer`. For existing provider access, choose **AI settings → Provider needs attention** (`settings-error`) and change **Provider state** in Controls. No provider requests, browser sign-ins, clipboard writes, commands, credential-file reads, disk persistence or model calls occur. Use only fictional credentials.

The MVP adopts OpenAI key/direct ChatGPT, Codex device authorization, Anthropic/OpenRouter key and custom/local endpoint interactions. Ordinary setup exposes only those methods. Cloud sources, subscription copy-code, other provider logins and arbitrary extensions remain separate explorations, visible through **Explore deferred providers and methods** in Controls or their historical starting states. Production catalog validation and native authentication qualification remain independent of these simulated flows.

## Development handoff

Use the ordinary provider flow, **AI settings** and **Conversation** as the implementation reference for [REQ-0015](../../requirements/data/requirements/REQ-0015-connect-user-provided-models.md). Do not promote the historical inventory wholesale or import workshop components into production. The [adoption procedure](design-workshop.md#adopt-an-approved-design) requires a separate production implementation approval.

| MVP methods                        | **Connect an AI provider → Choose provider** (`ai-providers`): OpenAI key or direct ChatGPT browser sign-in; separate OpenAI Codex device authorization; Anthropic/OpenRouter keys; compatible/local server with or without a key. Direct ChatGPT uses browser return, not a pasted redirect URL. |
| Independent accounts and servers   | **AI settings → Multiple accounts and servers** (`settings-connections`): add another account of an existing provider, rename it, choose the chat connection, reconnect it and remove one record. Compare the remaining account and both server addresses.                                        |

HTTPS does not need this consent.                                                                                                      |

Controls offer loaded, empty, excluded, failed and unavailable-discovery outcomes while the request is pending. Choices and connection identity survive these outcomes.                  |

Neither route imports another device’s access.                                                                                               |

### Connection identity and model lists

Connections are identified by stable local IDs, not provider names or labels. New records receive distinct default names; **Rename** changes only the visible name. Names must be nonempty and distinct within the workspace. Provider, authentication method and server address remain visible beneath the name. **Manage**, reconnect, forget and disconnect act on that record only. Adding another account does not select it while a selection exists. Removing the selected connection clears selection instead of selecting another account or managed access.

**Chat connection** explicitly selects the local default access. Each connection keeps its model defaults when switching away and back; a new connection starts at Recommended. An inherited conversation follows an explicit default-connection change. An explicit conversation model remains bound to its connection; it must not silently acquire another account’s credentials. Removing or forgetting its connection blocks subsequent requests without erasing its choice or draft. Connection labels appear in the chat model chooser so same-provider accounts remain distinguishable. Request snapshots are transient execution state, never per-message attribution.

**Refresh models** belongs to the selected connection. The UI distinguishes account/provider observations from the built-in compatibility list, and does not call listing an entitlement or credit check. Refresh shows progress, preserves explicit model choices and offers retry after failure. An excluded saved model remains visible with an explanation, not a replacement. Empty or unknown discovery leaves the connection saved; custom/local endpoints retain explicit model-ID entry. Results belong to the initiating connection/request and cannot recreate a removed record. Native discovery must replace these fixtures while preserving the same eligibility and ranking used for Recommended.

### Implementation and qualification boundaries

All operational configuration, model defaults, overrides, catalog state, credentials and endpoint consent belong to the workspace on this device. The approved requirements and this design do not adopt portable credential-transfer or configuration-transfer behavior from older production or architecture drafts. Reconcile those drafts before implementing storage; content synchronization and account recovery must remain distinct from AI access.

Persist HTTP acknowledgement for the exact approved destination with the local connection. Address changes require another decision before transmission. Do not infer permission for redirects, a TLS bypass or credential forwarding. The browser/device screens require correlated native results and confirmed local saving; returning to the app is not success. A provider limitation cannot be resolved by quietly substituting API billing for subscription access.

The workshop’s unit and Chromium/WebKit tests exercise synthetic state, keyboard interaction, reset, resizing and phone-sized geometry. They do not qualify real-provider access, native secure storage, iPhone authentication, Android lifecycle behavior or assistive technology. Managed account provisioning, billing and routing are not part of this provider-MVP handoff.

## Setup and workspace boundaries

AI setup is a focused standalone surface, visually continuous with workspace creation, without workspace navigation or settings controls. It uses the available app width, a quiet workspace-name header and a footer whose actions remain reachable while long forms scroll. Later connection changes reuse the authentication forms inside **Settings → AI & models**, retaining the category navigation and settings typography, controls and scrolling surface. They do not reopen the standalone setup shell. Chat only explains the Settings route; sending must not redirect into setup.

Standalone setup uses **Personal** and **Studio**. Conversation and Settings use the shared **Field notes** and **Reading room** workspace shell. Connection records, model choices, drafts and local notes remain workspace-scoped. Older standalone fixtures still expose Skip, its confirmation and continuation into a local workspace. They are not the initial onboarding contract: [REQ-0045](../../requirements/data/requirements/REQ-0045-create-local-workspaces.md) requires usable AI access before guided setup, with no manual-use bypass. Review the required route through `first-entry-ai` and `first-entry-model`. Loss of AI access in an established workspace still leaves stored content readable and manually editable.

Provider setup and model choice are separately editable. A conversation without an override inherits the workspace default, initially Recommended. The synthetic ranked catalog resolves its suitable model automatically, as specified in [REQ-0015](../../requirements/data/requirements/REQ-0015-connect-user-provided-models.md); absence of an override does not block chatting. Completing authentication or entering a credential is not yet confirmed access and durable configuration. An in-progress replacement keeps the previous usable connection until the replacement succeeds. Failure or cancellation leaves it unchanged. Unusable access remains gated until renewed. Abandoned attempts and late simulated callbacks cannot connect another workspace or revive an old attempt. Reopening uses only the current workspace's record; this is not a disk-restoration implementation.

Managed AI remains a distinct alternative, with no invented price, quota, account flow or access grant. Its handoff is reported outside the preview rather than simulated as a completed connection.

## Direct starting states

The `scenario` URL parameter identifies a starting state, including the existing `ai-*` and `settings-*` links. **Connect an AI provider** groups authentication methods, warnings and setup outcomes; **Conversation** groups the shared chat layout, response lifecycle and model/access conditions; **AI settings** groups provider management, model preferences and credential recovery. Controls follow the current screen after navigation, while **Scenario** and **Starting state** retain the selected preset.

| Suffixes                                                                 | Surface and recovery                                                                                                                                                    |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `offer`, `providers`, `methods`                                          | Legacy optional offer, searchable provider list with empty results, applicable authentication choices and Back; initial onboarding uses the required first-entry route. |
| `key`                                                                    | Required fields, masked/revealable synthetic secrets, provider-specific IDs and optional configuration.                                                                 |
| `browser`, `copy-code`, `device`                                         | Provider handoff, waiting, manual return where supported, optional enterprise domain, device challenge and cancellation.                                                |
| `cloud`, `endpoint`, `advanced`                                          | Explicit cloud credential sources, compatible/local endpoints, environment names, command permission and extension prompts.                                             |
| `connecting`, `success`                                                  | Pending access/save, cancellation, confirmed completion and user-controlled continuation.                                                                               |
| `warning`, `warning-device`, `blocked-subscription`                      | Provider/method warnings and a deferred subscription restriction within provider setup.                                                                                 |
| `cancelled`, `denied`, `expired`, `offline`, `save-error`, `unsupported` | Interrupted, rejected, expired, unreachable, unsaved or device-incompatible access with explicit recovery.                                                              |

**Conversation** has the empty, completed, working and failed-response states, plus missing access, catalog failure, no eligible models, an unavailable saved model and confirmed/uncertain save failures. Catalog loading, reasoning levels, a single available model, manual IDs and save outcomes are live controls rather than duplicate starting states. Legacy `ai-chat-*` links resolve to these Conversation states. Setup completion also enters this same view, including its pane tabs, spacing and composer.

Browser/device completion and saving are distinct simulated steps. Copy-code flows require input before completion. Device authorization does not ask the person to paste the displayed challenge back into Situate. Manual return is available only where the provider pattern supports it. [Authentication inventory and evidence boundaries](design-workshop-auth.md) describe the provisional provider fixtures; the production runtime's actual catalog and platform checks remain authoritative.

## Provider attention in Settings

`settings-error` uses the normal provider list, Chat settings and advanced disclosure. The provider’s status and recovery action change with **Provider state**; the existing Chat notice explains the selected provider’s problem. Missing, locked, denied and unavailable sign-in, expired access, changed rules and missing chat models are selectable states rather than separate scenarios. **Connected** shows the healthy comparison. Connection details remain available through **Manage**.

Storage retries stay in the overview. Authentication and restriction acknowledgement open after the corresponding action. A known session-displacing method cannot continue; the person must choose another method or provider. The same **AI settings** scenario also offers direct starting states for connection details (`ai-settings`, `ai-restored`), expired or inaccessible access (`ai-reconnect`, `ai-locked`, `ai-store-denied`, `ai-store-unavailable`, `ai-source`, `ai-access-denied`, `ai-capability`), an open restriction review (`ai-warning-changed`) and a blocked session-displacing method (`ai-session-replacement`). These links open inside Settings rather than a separate recovery surface. Loading a starting state replaces example data and pending work; **Reset scenario** restores that selected state, including its open review or method limitation. The `settings-error` preset resets to the expired-key example. `ai-missing` opens ordinary new-device setup with no copied provider configuration. `settings-local` and `settings-managed` compare a local endpoint with accountwide Situate AI availability; availability does not select it. The legacy `ai-chat-synced` link opens Conversation; `ai-chat-unconfigured` opens its missing-access state. Received replies carry no per-message model attribution and do not import future model selections. All operational AI preferences are scoped to the workspace on this device. See [provider access states](../../client/workshop/src/workshop/provider-access-design-notes.md) for review paths.

## Model choice

The model trigger sits in a compact row below the message input. It identifies the model for the next message rather than changing provider access or historical messages. In the product, a conversation without an override uses its workspace default; changing the model here saves that conversation's override under [REQ-0015](../../requirements/data/requirements/REQ-0015-connect-user-provided-models.md), not a new default for every chat. Long names truncate only on the trigger; accessible names and chooser rows retain the full name. Controls have at least 44px targets.

The shared Conversation composer keeps attachment and voice actions inside the input, with model and optional thinking controls below. The trigger shows Recommended, Workspace default or an explicit model. Provider and resolved-model details appear in the chooser and accessible description, not an additional paragraph below the input. The chooser is an anchored menu at desktop and phone sizes; a custom model ID uses a dialog. Both are clamped to the available app area, including keyboard occlusion.

The chooser displays the connection name and provider context, eligible synthetic records and an option to use the workspace default again. Choosing a row immediately starts persistence, closes the chooser and returns focus to the draft; there is no Apply step or automatic message. Escape/Close leaves the choice unchanged and restores trigger focus. An endpoint without discovery uses explicit model-ID entry rather than a fabricated catalog.

Selection and Send remain disabled until persistence is confirmed. Confirmed failure retains the previous explicit or inherited choice and permits retry or keeping that choice. An uncertain save makes no rollback claim: submission stays blocked until retry or readback establishes the stored value. New or previous readback results preserve draft and history. A running response or an unsaved response does not block model or thinking changes for the next request. Response lifecycle and selection persistence are independent: completing or stopping a response does not settle a pending model save, and saving a choice does not change or restart the active request. Completing the simulated response lifecycle generates no AI output.

No eligible models, catalog failure, an unavailable saved ID and disconnected access are distinct states. One eligible model needs no initial selection step. A custom endpoint without a discoverable suitable model requires a configured default or explicit ID, rather than a guessed model. Missing access gates click, Enter and form submission; it cannot borrow access from the other workspace.

### Thinking level

For a model with adjustable thinking, **Advanced settings → Chat model** is followed by **Thinking level**. Recommended resolves the maintained level for that model; only supported levels are offered. The field remains visible but disabled when thinking cannot be adjusted. A short explanation distinguishes a model without adjustable thinking, unknown controls for an endpoint/model, and missing local access. Managed AI retains its separate automatic-model presentation.

With **Show model picker in chat** enabled, the composer offers model and thinking selection together when the chosen model has adjustable thinking. Otherwise the chat omits the thinking control. Both selections remain editable during an active response and apply only to subsequent requests. A conversation inherits its model’s workspace thinking default until it chooses its own level. The first menu option restores inheritance; Recommended remains available independently when the workspace default is an explicit level. Preferences are retained per model, so switching to a non-thinking model hides the control without erasing another model’s choice. Hiding the chat picker changes visibility, not preferences. Defaults and overrides remain workspace-and-device-local, and an active request keeps its captured level.

In **AI settings**, use the live **Model choice example → Three thinking levels** control, then expand Advanced settings. This selects OpenAI’s synthetic **Example Reasoning** model. **Without adjustable thinking** provides the comparison. In **Conversation**, use **Reasoning model · three levels** or **Reasoning model · two levels**. The shared capability table and recommendations are design fixtures, not live-provider capability or entitlement evidence.

## Accessibility and review

Exercise setup and chat at desktop, phone and short-window sizes using the workshop controls. Platform/environment changes preserve drafts and focus; loading a starting state or resetting its scenario restores fixtures. Profiles simulate available space, not platform fonts, native callbacks, keyboards or assistive technology.

Use semantic labels, linked field errors, textual status and focus containment. Transitions focus the heading; validation focuses the affected field. Search retains focus while results change. Required actions remain reachable above keyboard occlusion. Reduced motion retains the same welcome/completion content. Success follows confirmed access/save only; errors and skipping do not use disappointed artwork.

Run `npm run test:design` and `npm run test:browser:design` from `client/`. These tests cover synthetic contracts and rendered interactions, not real account access, entitlement, credential security or cross-device portability.

## Decisions and open questions

The selected direction is required standalone connection setup before guided onboarding, integrated connection management inside Settings during normal use, workspace-and-device-local access and a separate next-message model choice. Older optional standalone fixtures do not authorize an initial manual-use bypass. This is a design direction, not a usability finding. Reopening incomplete onboarding retains the saved interview but requires usable access on the current device; it does not replay interrupted requests.

Restrained welcome/completion feedback, explicit credential-source choice, draft retention, staged replacement, removal confirmation and abandoned-attempt handling are interface proposals. They do not select a storage cipher, keychain strategy, command sandbox or recovery protocol. Credential removal is not provider revocation; cancellation cannot undo provider consent.

Selected authentication methods on every target, workspace-and-device-owned refresh/caches, device-local secure storage and active/unsaved-turn coordination require production verification. Dynamically registered providers, external credential sources and managed account access are separate deferred integrations. A saved connection or listed model does not prove entitlement or functional compatibility. Never perform a billable model call merely to make a synthetic success state convincing.

Relevant approved requirements: [REQ-0045](../../requirements/data/requirements/REQ-0045-create-local-workspaces.md), [REQ-0015](../../requirements/data/requirements/REQ-0015-connect-user-provided-models.md), [REQ-0037](../../requirements/data/requirements/REQ-0037-keep-workspaces-independent.md), [REQ-0038](../../requirements/data/requirements/REQ-0038-copy-portable-workspaces.md), [REQ-0013](../../requirements/data/requirements/REQ-0013-synchronization-service.md), and [REQ-0016](../../requirements/data/requirements/REQ-0016-managed-ai-access.md).

A useful usability test asks someone to retain a draft, change its next-message model, recover from an uncertain save, and explain which messages and workspace are affected. Separately, check that initial guidance cannot bypass required access, and that an established workspace with unavailable AI still permits local manual work and access recovery through Settings without borrowing another workspace's connection.
