# Provider and authentication coverage

## Evidence boundary

This inventory was captured before the production provider/authentication integration. It describes the exploration’s reference release, not the current client’s shipped support matrix. [The architecture](../architecture/04-solution-strategy/application-and-agent.adoc) selects Pi Agent Core and leaves credentials and provider adapters to Situate. The development harness is not the product runtime; current production catalog and platform checks remain authoritative.

The fixture inventory is an exploratory snapshot, not a verified inventory of Pi AI/Agent Core 1.1.0. Reconcile it with the product lockfile and generated catalog before using it as implementation guidance. The MVP deliberately selects fewer integrations; the broader inventory is research, not its release checklist.

Reference material includes Pi's provider, model, SDK, configuration, custom-provider, security and llama.cpp documentation and the credential SDK example `examples/sdk/09-api-keys-and-oauth.ts`. Public counterparts are in [Pi documentation](https://github.com/earendil-works/pi/tree/main/packages/coding-agent/docs); that moving branch is not evidence for a pinned product release.

The inventory derives from `pi-ai/dist/providers/all.js`, provider auth definitions, `auth/types.d.ts`, and OAuth interaction events in `auth/oauth/`. These are metadata contracts, not evidence of a successful login or provider request. No provider implementation is bundled in the workshop.

The MVP in [REQ-0015](../../requirements/data/requirements/REQ-0015-connect-user-provided-models.md) selects OpenAI API-key/direct ChatGPT access, distinct Codex device authorization, Anthropic/OpenRouter API keys and custom/local endpoints with optional keys. Other methods below are deferred; conversational Pi parity is a long-term goal. The MVP excludes classifiers, permits multiple same-provider connections, selects ranked automatic initial models and uses acknowledged warnings instead of a policy-only hard block. The fixtures still include older alternatives; they are not all adoption-ready. Same-phone setup and native lifecycle behavior require separate platform qualification.

## Default provider selection

Ordinary setup offers OpenAI API keys or direct ChatGPT browser sign-in, OpenAI Codex device authorization, Anthropic and OpenRouter API keys, and compatible/local server addresses with optional keys. Codex is a separate connection type, not an OpenAI browser alternative. Custom/local connections without discovered models retain explicit model-ID configuration.

The controls-only **Explore deferred providers and methods** switch reveals the historical inventory. Deferred starting states, including Orbit security examples, enable that mode explicitly; their existing deep links remain available. These fixtures are interaction studies, not supported-product claims.

HTTP server setup stops at **Connect without encryption?** before any simulated connection or credential dispatch. It displays the normalized destination and explains exposure of prompts, chat contents, responses and keys. **Connect to this address** consents only to that destination. **Back to address** retains entered values and the previous saved connection. Editing the address invalidates consent; cancellation and reset discard it. HTTPS skips this warning. Invalid URLs, embedded credentials and URL fragments are rejected. This simulation does not qualify redirect handling, TLS validation or real transport security.

Connection records may carry a stable `id` and optional `label`. Successful reconnect or replacement retains both; a label identifies the connection in its details header, with provider and authentication underneath. Selecting an already connected provider remains possible for an additional independent connection. Settings owns connection creation, naming and per-ID records.

## Interaction contract

`AuthPrompt` covers `text`, `secret`, `select` and `manual_code`. `AuthEvent` covers `info` (optional links), `auth_url`, `device_code` and `progress`. Shared form, handoff, waiting, progress and error surfaces handle these families without a bespoke screen per provider. Provider options and prompts may be multi-step, conditional and extension-defined; expose the options actually returned, honor per-prompt cancellation, and treat provider strings/URLs as untrusted data. Do not turn instructions or links into automatic command execution.

The ordinary flow is provider → available methods → fields or provider handoff → pending access/save → success. Entering a credential, returning from a browser, or finding a local profile is not itself proof that connection succeeded. A late callback must be correlated to its originating workspace and active attempt; it cannot unlock another workspace or revive a cancelled attempt.

Pi defaults to an agent-wide `auth.json`, accepts environment fallbacks and has command-output caching. Those defaults do **not** satisfy Situate workspace independence. The host must supply workspace-and-device-owned credential/configuration storage outside portable workspace files and explicit local resolution, including refresh and concurrency behavior. Never infer authorization for an unconnected workspace from process environment or another workspace’s cache. The standalone AI example keeps separate in-memory workspace records; Settings composes connection records for its connection-management scenarios.

Provider-scoped configuration and saved source references stay outside the portable workspace directory and history, scoped to the workspace on this device. An external profile, environment source, command executable or credential file may remain device-dependent. The design proposes explicit selection before using such a source. It does not promise shell execution, AWS profiles, ADC files or localhost callbacks on mobile. Missing prerequisites produce the method-unavailable state, not silent fallback to another workspace or provider. The selected MVP methods need native platform qualification; unavailable states do not satisfy that requirement. Deferred sources and extensions do not block MVP completion.

## Chat model eligibility

[Workshop model fixtures](../../client/workshop/src/ai/) uses synthetic catalog records to demonstrate provider, authentication, chat-capability and platform filtering. The records are not real model IDs and must not become a production allowlist. Fresh connections use the workspace default, initially Recommended, without creating a conversation override. A suitable model is resolved from eligible ranked records in the background. A stored override remains separate from connection configuration. Custom endpoints without discovery need a configured default or manual model ID. No catalog is fabricated for such endpoints.

A listed model is not proof of account entitlement or function compatibility. The runtime’s eligible catalog may differ by authentication method and platform. Loading failure, zero eligible models, unavailable selected IDs and disconnected access remain distinct. Moving selection to chat does not expand authentication support or eliminate device limitations.

## Credential boundaries

The [provider access scenarios](../../client/workshop/src/workshop/provider-access-design-notes.md) explore provider-specific own-risk warnings, blocked methods, device credential states and distinct removal scopes. Official synchronization, account recovery and sync-device authorization are outside the current workshop scope; provider device-code login is a starting state of **Connect an AI provider**. These are simulated interactions, not native credential storage, cryptographic provisioning or provider permission.

- Provider credentials, connections, endpoints, selected access and future model choices are device-local for every method. Neither directory copies nor official/custom synchronization transfer them. A new device offers ordinary setup; it does not show a copied connection as broken.
- Account recovery restores eligible workspace content, not local AI access. Messages have no per-message provider/model attribution; received content does not select the next request’s access. Situate AI entitlement is accountwide, with separate device sessions and explicit local selection.
- Own-provider credentials stay on end devices. Situate services do not store, refresh or proxy them. A method known to displace another device’s session cannot continue as independent-device setup. Actual provider sign-in, renewal and revocation semantics still require qualification.
- Removal forgets the connection only for this workspace on this device; it is not provider revocation. Cancellation stops Situate’s attempt; it does not undo provider-side consent.
- Secret inputs are never included in settings summaries or review messages. Resetting a scenario or reloading its controls discards fixture state; reloading only the preview retains the controller's current state. Do not use real credentials.
