Windows, Linux desktop and Android columns retain historical component evidence for deferred targets, not active product qualification.

## Shared implementation boundary

### Connection and credential persistence

Device-local application storage owns the versioned connection manifest, selected connection, per-connection settings and conversation-specific overrides. A device-local registry assigns a namespace to the canonical workspace location; neither an AI identity nor provider configuration is written into the portable workspace. Multiple accounts of one provider and multiple custom endpoints have separate IDs. New defaults retain Recommended; existing explicit choices and active-run snapshots are not replaced after catalog changes or request failures.

[Core connection storage](../../client/crates/situate-core/src/ai_connections.rs) keeps credential ciphertext and its publication journal in device-local application storage, outside the workspace. XChaCha20-Poly1305 authenticates the stable workspace ID and complete connection record, including configuration revision. Fresh 32-byte keys are stored and read back through the OS backend before publication. This local format is not an official-synchronization credential format or recovery vault.

Device-local associations authorize a particular canonical workspace location. Reopening that location restores its AI configuration. A new device or a copied or moved location offers ordinary setup without inheriting the source's credentials. Credential locks follow the local namespace rather than only a window. Automatic transfer after moving a workspace is not supported.

A prepared/publishing journal retains replacement ciphertext through cross-store publication failures. Recovery checks the local manifest, preserves unrelated records and selections, and rejects conflicting edits instead of overwriting them. Before renewal dispatch, native code captures the manifest and authenticates the exact connection record and in-memory credential against its decrypted payload. A returned grant is staged against that captured record before reconciling external changes; removal or configuration changes retain a recoverable conflict rather than resurrecting or overwriting the connection. Fixtures cover denial, restart, stale journal replay, explicit conflict discard and rotation after request cancellation. These are tested recovery semantics, not a claim that all filesystems, power-loss cases or backup systems are qualified.

See [ADR-0002](../architecture/09-architecture-decisions/0002-portable-workspace-credentials.adoc) for local mechanisms and the boundary with content synchronization and recovery. Its status remains Proposed.

### Model discovery and selection

The reviewed [recommendation catalog](../../client/app/src/ai/model-recommendations.json) is separate from the generated [model inventory](../../client/app/src/ai/catalog.generated.json). It records provider/authentication pairs, source links, rationale, eligibility and explicit chat/comment priorities. Both are bundled application inputs; recommendations are not fetched at startup. A listing, eligibility label or price does not establish authentication, account entitlement or live model capabilities. A pinned provider alias does not guarantee immutable model weights.

[Native discovery](../../client/app/src-tauri/src/ai_discovery.rs) distinguishes account-filtered lists from provider observations. Direct ChatGPT reads `/v1/models`, taking `models[].slug` only where `visibility` is `list`; OpenRouter uses `/api/v1/models/user` with text-output filtering. OpenAI API-key and Anthropic authenticated catalogs, and a custom endpoint's `/models` response, are provider observations rather than proof of inference entitlement. Codex uses static compatibility only and makes no account-discovery API claim. These contracts have deterministic fixtures, not live-account qualification.

Discovery runs during connection setup and through explicit native refresh. Observations are cached inside the encrypted, device-local connection payload, isolated by connection ID rather than written as an account model list into workspace metadata. Storage rechecks the captured configuration before saving; discovery cannot replay a changed connection. Expired direct grants are durably renewed before discovery, independently of whether the subsequent catalog request succeeds.

A result is complete within bounded time, page, byte and model limits or becomes unknown. Denials, malformed responses, redirects, stalled requests and incomplete pagination do not become authoritative empty lists or partial availability claims. Only complete account-filtered lists exclude absent IDs at native admission; provider observations and static catalogs do not assert entitlement. An excluded saved choice remains saved and requires user resolution rather than implicit replacement.

[Recommended selection](../../client/app/src-tauri/src/ai_settings.rs) intersects observed IDs with supported, ranked catalog candidates, resolving chat and economical comments independently without turning Recommended into an explicit preference. Unknown or empty discovery does not invent a model. Codex may resolve from its explicitly static source; custom IDs are never guessed. Explicit choices and active-run snapshots remain unchanged. Model and thinking overrides are local to each conversation; a workspace-default change does not rebind an explicit override to another connection. Explicit refresh is not a model/provider fallback, and request failure never silently changes the selected model.

[Native resolution](../../client/app/src-tauri/src/ai_settings.rs) attaches the catalog revision to the concrete model choice for recommendation attribution. This is not a durable record of every recommendation used: Recommended remains symbolic in saved settings and resolves before request admission. Concrete settings that carry `catalogRevision` retain it in [device-local connection storage](../../client/crates/situate-core/src/ai_connections.rs), including an older revision when reopened. [Conversation overrides](../../client/app/src-tauri/src/ai_preferences.rs) store the connection and model ID, not that revision. Active-run choices are transient; neither they nor catalog attribution become portable per-message history under [REQ-0015](../../requirements/data/requirements/REQ-0015-connect-user-provided-models.md).

### Native request and session ownership

[Native AI admission](../../client/app/src-tauri/src/ai.rs) binds requests to the workspace, connection, configuration revision, model and destination. Codex bearer/account headers are injected natively; direct ChatGPT credentials use their separate grant and verified identity. Redirects and ambient proxies are rejected. Public status and normal response frames do not expose credential records.

The [provider-platform plugin](../../client/crates/tauri-plugin-provider-platform/src/lib.rs) rejects JavaScript invocation rather than relying only on a missing capability grant. Native callers own secure-store operations and authentication-browser callbacks. A browser return is not authentication success.

[Workspace authorization sessions](../../client/app/src-tauri/src/workspaces.rs) are native-held, non-deserializable generation tokens. A new authorization captures the current scoped session. Continuation can complete for that still-open originating session after a mobile workspace switch, but must retain its operation lease and pass window, Arc-generation and quit checks. Closing and reopening the same workspace ID does not revive the token. Ordinary workspace commands remain current-bound.

Custom HTTP requires acknowledgement bound to the normalized destination; editing the destination invalidates that consent. HTTPS retains certificate verification. Consent does not permit credential-bearing redirects or arbitrary provider headers. A custom server without discovery requires a real user-supplied model ID; no model name is guessed.

### Workspace locations

Desktop filesystem workspaces and mobile app-local document workspaces have a real writable root. Mobile `android-documents` and `ios-documents` use the native `localRoot` operation through [files::local_root](../../client/app/src-tauri/src/files.rs); they are not temporary copies of an external workspace.

External `android-tree` and `ios-bookmark` workspaces remain read-only. They do not supply the writable root needed for conversation persistence and AI-assisted file changes. Connection configuration remains in device-local application storage, but secure-store availability alone does not qualify AI use in those locations. Writable external-document support remains a separate product gap.

## OS evidence and remaining limits

The [platform adapter](../../client/app/src-tauri/src/provider_platform.rs) implements non-synchronizing macOS Keychain, Windows Credential Manager, Linux Secret Service, and native iOS/Android plugin calls. Windows uses current-user generic credentials with local-computer persistence; it is not a custom DPAPI file format. Linux explicitly reports absent service or locked collections. Source existence does not establish OS installation, lock, signing, upgrade or backup behavior.

On iOS, wrapping keys use non-synchronizing `AfterFirstUnlockThisDeviceOnly` Keychain items without routine authentication prompts. Device-local ciphertext is excluded from backup and uses first-unlock file protection. The isolated [iOS lifecycle harness](../../client/crates/tauri-plugin-provider-platform/ios/LifecycleHarness/README.md) provides observed simulator evidence:

- Production authentication coordinator plus a Rust loopback server and a synthetic redirect delayed for 40 seconds, with continued foreground execution and explicit browser dismissal after callback receipt.
- Cancellation through the system authentication UI.
- Real simulator Keychain save/read/delete using an isolated ad-hoc-signed access group, a fresh UUID account and a random 32-byte value; no existing-account enumeration.
- Injected secure-store and browser-coordinator ownership/error tests.

These component results do not qualify production signing/access groups, physical-device backup protection, background execution, locked-device behavior, a provider's redirect acceptance, or a full Situate enrollment-to-request journey. The separate full application Simulator journey above exercises encrypted credential storage and cleanup. Simulator apps need a valid ad-hoc signature: disabling codesigning produced Keychain status `-34018`, while the signed application verified missing keys after cleanup. The SDK does not promise indefinite execution or automatic HTTP-loopback completion; Rust owns completion and closes the authentication session.

Android implements Keystore-backed AES-GCM protection for wrapping-key records in no-backup storage, native browser handoff and local-network permission handling. The isolated [Android lifecycle harness](../../client/crates/tauri-plugin-provider-platform/android/LifecycleHarness/README.md) used a disposable API 36 ARM64 emulator and the production `ProviderKeyStore` source and a fresh UUID account with a random 32-byte value. It verified save/read equality, a synthetic AndroidKeyStore AES alias with no encoded key bytes, persistence by digest equality after force-stop/relaunch into a different process, deletion followed by missing-item behavior, and removal of that exact alias and fixture metadata. The fixture used an isolated application UID. This is real emulator Keystore evidence, not physical hardware-backing, backup or full product qualification.

**Android foreground-service components:** the production `specialUse` foreground service and Rust listener ran in the same isolated API 36 ARM64 emulator process. With Chrome's unaccepted first-run screen foreground, guest-shell callbacks reached the listener after at least 43 seconds in all four scenarios: notification permission denied, permission granted, an actually user-blocked previously published notification channel (`importance=0`), and the last Activity destroyed. The granted-permission scenario exercised the published notification's Cancel `PendingIntent`. A synthetic JNI recorder observed cancellation while the service remained alive during a synthetic drain hold. Explicit finish through the production Rust/JNI bridge uses cached VM/class references rather than a live Activity. It acknowledged removal of the service, including after a ten-second hold following Activity destruction. Keystore persistence and exact fixture cleanup passed again.

Without the service, the baseline process was cached and frozen about 15 seconds after external browser handoff, with Rust heartbeats stopping at approximately 10.2 seconds. With the service, the observed probes were neither cached nor frozen. The baseline had no measured callback-on-return result. The service observations establish bounded process/listener liveness under those conditions, not a browser-originated redirect or successful provider enrollment.

The fixture runs the production service, coordinator and Rust/JNI finish bridge, but not the full Tauri login controller. The production cancellation channel is source-verified (`Channel.send` → PluginManager native `sendChannelData` → Rust callback, without WebView execution) and covered by Rust callback/IPC unit tests. It is not full-app device runtime evidence for that channel, a real credential commit or a completed login.

`POST_NOTIFICATIONS` is optional: the implementation declares it but does not prompt for it or gate authentication on a grant. Denial or a blocked channel may hide the notification drawer's Cancel action. In-app cancellation remains available on return; Android's Active apps Stop force-stops the app rather than gracefully draining native work. Notification content contains no URLs, OAuth state, codes, accounts or tokens. The 300-second native deadline cancels waiting but does not tear down the service during Rust drain.

**Android browser enrollment: blocked, not run.** Chrome was the sole installed `ACTION_VIEW` resolver and required first-run Terms of Service acceptance, including its use-without-an-account route. No terms were accepted and no browser page or browser-originated callback ran. Guest-shell probes do not close that gap. API 37 local-network permission, physical hardware-backing/backup behavior and Play review of `specialUse` remain unqualified. Same-phone authorization/request/renewal journeys still need separate qualification. Windows and Linux likewise need native-platform runtime qualification beyond their source/host harness checks.

## Provider sources and security checks

Provider documentation and source inspection establish contracts to test, not successful account access or permission to reuse another application's registration:

- OpenAI's [OSS/local integration](https://developers.openai.com/siwc/token-sharing-open-source) and [registration guide](https://developers.openai.com/siwc/token-sharing-open-source/sign-in) describe actual app naming, stable per-host identity, dynamic registration, issued-client reuse, loopback return and granted direct-use scope. Paid/remote usage has a separate approval route; arbitrary mobile redirects are not established. Native signed ID-token checks cover trusted issuer/key, audience, expiry, subject and attempt nonce; synthetic signatures do not establish registration acceptance.
- OpenAI's [session guidance](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions) requires serialized refresh using the latest token. Its [VM transfer guidance](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms) assigns refresh ownership to the destination while retaining distinct host identity; it does not authorize concurrent rotating replicas.
- Anthropic's [credential policy](https://code.claude.com/docs/en/legal-and-compliance) prohibits third-party Claude.ai login/token intermediation and identifies API keys and supported cloud providers as integration routes. Subscription access is deferred; acknowledged risk does not change those terms.
- OpenRouter's [PKCE guide](https://openrouter.ai/docs/guides/overview/auth/oauth) describes user-controlled API keys, localhost callbacks and headless copy-code with mandatory PKCE when no callback URL is supplied. That deferred flow is not device-code polling or a renewable subscription.
- [OAuth for native apps](https://www.rfc-editor.org/rfc/rfc8252.html) calls for system-browser/authentication-session handoff rather than a credential-capturing embedded WebView. Codes, state, PKCE and nonce remain bound to the initiating attempt; return alone cannot authorize access.

The product's `client/Cargo.lock`, `client/package-lock.json`, app-owned `catalog.generated.json`, `provider-policy.json` and `transport-contract.json` are versioned runtime/admission inputs. Rig is pinned to 0.46.0; Pi AI and Agent Core are not product dependencies. Recheck native provider definitions, authentication branches, request construction, stream assembly and redistribution terms against those inputs when dependencies change. A moving upstream branch, development harness installation or old workshop fixture is not equivalent evidence.

Selected protocols are OpenAI Completions/Responses, Anthropic Messages and Codex Responses SSE. Codex uses native bearer/account injection, request construction and SSE assembly. No provider parser or transport depends on a frontend SDK. Deferred Google/Vertex SDK transport and AWS signing/event-stream paths are not qualified by these adapters; a generic endpoint field does not establish cloud-provider parity. Native credentials must not be exposed to the WebView or ambient SDK credential chains. Published client identifiers and source licensing do not establish service entitlement or permission for Situate to reuse a registration.

## Release gaps and provider conditions

The default MVP repository runner (`node tools/test.mjs` from the repository root) covers native smoke launches, synthetic native-agent flows with reopen and cleanup, product browser tests, unit tests, Clippy and dependency/license/audit checks. Locked-image screenshot comparisons remain explicit or extended checks; iOS application verification is a separate command. Passing this gate does not replace the missing platform and live-access qualification in the matrix.

The macOS native smoke and native-agent flows require an unlocked desktop throughout execution. The runners reject a locked or unavailable desktop before building or launching. Successful local and VM runs do not qualify execution while the operating system is locked.

Further gates are:

1. Packaged setup → durable save → suitable model → synthetic request → reopen → renew/re-authenticate → remove on each claimed platform, including duplicate-account isolation and failures.
2. Apple physical-device/production-signing checks, mobile suspension, background expiration and lock behavior beyond the observed Simulator conditions. Deferred targets require a separate scope decision and their own native verification before support resumes.
3. Destination-specific LAN permission/HTTP-consent journeys and writable external-document workspaces where required by the release scope.
4. Live qualification of implemented model discovery and separately authorized evidence of accepted registrations, grants and model entitlement. Static catalog support must never be presented as verified account access.
5. A passing aggregate repository gate, retaining passing product and visual coverage, before any complete MVP release claim.

No reviewed restriction currently requires a provider-specific own-risk warning for a selected MVP method. Unknown Codex registration/client-reuse permission is not an established prohibition. If a concrete restriction is identified, REQ-0015 still requires its source, consequences and explicit acknowledgement before affected use. The documented Anthropic subscription-token prohibition remains unchanged, but that method is deferred; it does not justify blocking Anthropic API keys or adding a warning to an unrelated selected method.

Official content synchronization's encrypted provisioning and account recovery remain separate from this local implementation. Neither official nor custom synchronization transfers provider credentials or operational AI settings. Partial releases must name their platform, workspace-location and method gaps rather than treating source coverage as completion.
