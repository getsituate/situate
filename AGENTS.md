# Repository guidelines

Situate is developed as a public, open-source project. Treat every tracked file, commit, issue, and build artifact as potentially public. Public visibility does not replace explicit licensing; preserve third-party terms and do not assume redistribution rights.

## MVP platform scope

- macOS is the only active product target. iOS, Windows, Linux desktop and Android are deferred and are not currently supported. Ordinary development does not need their SDKs, packaging, platform-specific compatibility fixes or CI gates unless explicitly requested.
- Preserve useful existing platform code and tests unless removal has a concrete benefit. Deferred targets are not supported or qualified by passing shared tests. Reintroducing a target requires an explicit scope decision and native verification.
- Linux may still host shared CI tooling, security scans and other platform-independent checks. A CI host is not a product support commitment. Browser tests do not replace native macOS qualification; shared or historical mobile checks do not establish current iOS support.
- Use the default MVP test scope for development and PR verification. Expensive workshop, design-browser and screenshot sweeps are opt-in through `node tools/test.mjs --extended` or their dedicated commands. Run focused deferred checks when changing the behavior they cover; do not present an MVP pass as exhaustive coverage.

## Released data and compatibility

- Situate is publicly available. Treat workspaces and device-local application data created by published versions as user data, including conversations, drafts, queued inputs, file references, history, plugin state, settings and provider connections.
- Follow [REQ-0069](requirements/data/requirements/REQ-0069-preserve-workspace-version-compatibility.md) and [REQ-0070](requirements/data/requirements/REQ-0070-preserve-plugin-api-compatibility.md): preserve workspace and public plugin-interface compatibility for at least six months from each app version's publication. This is a minimum, not an expiry date. A one-way migration must not break required mixed-version workspace use.
- Before changing a persisted format, inventory its readers, writers and released versions. Preserve supported data through compatible evolution or a tested migration with recoverable failure and interruption behavior. Never replace unreadable data with empty state, silently reset a workspace or discard retained user state to simplify an upgrade.
- Pre-release exceptions in ADRs and implementation plans apply only to formats verified never to have shipped in a public release. They do not exempt later changes to published formats. If release provenance is unclear, preserve compatibility until it is verified.
- Format changes require synthetic fixtures matching supported published versions and upgrade/reopen tests, including skipped releases, interrupted or failed migration and preservation of unknown fields during mixed-version writes. See [release compatibility verification](docs/development/testing.md#release-compatibility-verification). Fresh-workspace tests alone are insufficient; report unavailable release fixtures or native verification as gaps.

## Language

- Write repository documentation, requirements, code, comments, tests, examples, agent instructions, and commit messages in English. Product translation catalogs are the exception: their values use the catalog's language. Keep supplied UI copy and user-facing errors in the central localization catalogs rather than inline in code.
- Use English names for new files and directories. Preserve stable requirement IDs, external identifiers, URLs, proper names, and legally required notices.
- Do not introduce instructions that switch repository content to another language. Conversation language may follow the user's preference.

## Privacy and security

- Never commit credentials, tokens, private keys, customer data, raw interviews, personal correspondence, or confidential business records.
- Publish research findings as reviewed, non-identifying summaries. Removing names alone is not anonymization; consider indirect identification and information about third parties.
- Keep private source material outside this repository. Do not embed private workspace paths or links to confidential records in public documents.
- Infrastructure definitions may be public. Keep secrets, Terraform state, saved plans, sensitive variable values, database dumps, logs, and production data out of version control.
- Keep application, build, test, and release scripts independent of secret managers. Users supply credentials through explicitly supported environment variables or the Git-ignored `.env` in the repository root; choosing a secret manager and populating these inputs is the user's responsibility. Do not add direct 1Password access, secret-manager CLI requirements, or automatic secret fetching to repository scripts.
- Parse `.env` as data, never source or execute it. Consume only the variables needed by the operation, let explicitly set environment variables take precedence (including empty values), and use environment-only credentials in CI. Keep `.env` private (`0600` on POSIX), preserve unrelated entries when editing it, and never include its values in logs, artifacts, commits, or subprocess environments that do not need them. Committed `.env.example` files may contain variable names and empty values or synthetic placeholders, never real credentials.
- Review new dependencies, copied code, images, fonts, and other assets for redistribution rights. Preserve license and attribution requirements.
- If sensitive information is found in tracked content or history, stop publication and report it without repeating the sensitive values. Removing the current file does not remove prior commits. Rotate exposed credentials where applicable.
- Do not publish branches, tags, historical refs, or artifacts without explicit authorization and a review of the exact content and history being published.

## Product and documentation

- Keep product code, public documentation, and reusable deployment definitions together where useful. Confidential records do not belong in the monorepo.
- Preserve the meaning and stable IDs of goals and requirements. Separate confirmed decisions, hypotheses, and open questions; do not invent evidence or commitments.
- For branded interfaces or artwork, start with `design/brand/README.md` and reuse its canonical tokens, Bend geometry, and motion guidance. Keep exploratory departures separate from the brand sources.
- Keep links and examples working when files move. Write for readers who do not have access to private conversations or notes.
- Do not record task narration, compliance claims, or conversation history in product copy, comments, or documentation.

## Delegation

- Use Herdr for delegated tasks. Load `.pi/skills/delegate-with-herdr/SKILL.md` before starting another agent.
- Run read-only reviewers in separate panes and give every editing delegate its own Git worktree. Review and test changes before integrating them.
- Run the parent agent inside Herdr; if Herdr is unavailable, follow `docs/development/README.md` rather than silently using another delegation mechanism.

## Visual regression tests

- Reuse product Playwright flows in `client/app/tests/browser/`. Mark selected tests with `@visual-desktop` or `@visual-mobile`, use `localizationMode: "real"`, and call `await visual.capture("area.state")` after asserting that the intended state is visible. Import `test` from `./test`; do not duplicate flows in a separate screenshot suite or capture only the final state of a multi-step test.
- Capture meaningful intermediate states, including dialogs, empty results, and errors. Choose stable state names independent of test titles. References are separated by desktop/mobile profile, actual viewport size, and locale. Different data, focus, or interaction states need distinct names; identical states can share a reference during checks, but baseline updates reject duplicate writers.
- Normal browser runs keep the functional assertions and do not compare screenshots. `cd client && npm run test:visual` runs all tagged tests and compares their checkpoints in the locked Linux/amd64 Docker image. Do not generate product reference images using host-native Playwright or change the image to bypass a mismatch.
- For an intentional visual change, run `cd client && npm run test:visual:update` to execute all tagged tests and regenerate all their references. Scope an update with `-- --project mobile --grep 'provider selection'` when appropriate. Then run `npm run test:visual` and inspect the changed PNGs before committing them with the code change. Do not update references merely to silence unexplained failures.
- Open local comparisons with `cd client && npm run test:visual:report`. Missing references and visual differences fail checks; CI never updates references. Keep fixtures synthetic and never capture personal workspaces or credentials.
- When removing or renaming a checkpoint, review and remove its obsolete reference images. See [Visual regression tests](docs/development/testing.md#visual-regression-tests) for fixture usage, duplicate handling, Docker prerequisites, and CI reports.

## JavaScript toolchain

- Keep dependencies local to each worktree; do not symlink `node_modules` to another checkout. From the repository root, use `node tools/npm-ci.mjs [client|requirements]` for installation or reinstallation so it waits for tests in that worktree. Raw `npm ci` does not participate in the command queue and can remove dependencies used by a running check.
- The test runner, automatic Pi checks, and dependency preparation share a per-worktree queue. Use `node tools/run-coordinated.mjs -- command arguments...` for additional artifact-writing test/build commands. Do not run several uncoordinated commands against the same checkout or kill supervisors directly. Use suite deadlines rather than short outer timeouts for broad checks; allow cancellation to finish cleaning up owned processes. Separate worktrees remain parallel. See `docs/development/testing.md` for native desktop coordination and optional Cargo-cache isolation.
- Use Volta for every Node.js, npm, and npx invocation, including dependency installation, tests, builds, and agent startup. Install and configure it as described in `docs/development/README.md`; keep its shims first on `PATH`.
- The root `package.json` owns the exact Node/npm pins; nested packages inherit them through `volta.extends`. Do not bypass them with system executables, another version manager, or a global npm upgrade. Check `node --version`, `npm --version`, and `volta which node` when diagnosing toolchain failures.
- Change pins deliberately at the repository root and keep compatibility pins, container inputs, and toolchain contract tests aligned.

## Commit messages

- Use an English Conventional Commit subject: `type: summary` or `type(scope): summary`. Allowed types are `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore` and `revert`. Scopes are optional and have no fixed list.
- Keep one coherent change with its relevant tests and documentation. Describe observable behavior for product changes; add a body explaining why or the prior failure when the subject is insufficient.
- Mark incompatible changes with `!` before the colon or a `BREAKING CHANGE:` footer, and describe the incompatibility. A marker does not authorize a compatibility break.
- Do not invent user benefits for internal changes, require release prose or custom changelog trailers, or include credentials, private observations, personal paths, tool signatures or process narration.
- Follow [commit conventions](docs/development/commit-conventions.md) for Git-generated merge/revert exceptions, squash subjects, grandfathered history, range checks and optional local hooks. Do not rewrite old commits merely to satisfy the convention.

## Changes and verification

- Keep changes scoped and preserve unrelated work.
- Run the relevant validation, tests, and build after changes. Report any checks that could not run. Use `node tools/test.mjs --quick --changed` for dependency-free feedback with a five-second total budget. Keep checks that exceed that budget in `--feedback` or another longer-running suite; do not raise the quick deadline or treat a timed-out check as passed. Run `node tools/test.mjs --feedback --changed` for affected unit, lint/format, and type checks; quick feedback does not replace them. See `docs/development/testing.md` for selection and prerequisites. Ordinary documentation and concepts require formatting and document checks, not application tests or builds. Requirements records retain catalog validation; prompts, fixtures, and Pi instructions retain their consuming tests.
- Before creating a pull request, run `node tools/test.mjs --changed --base origin/main` from the repository root using an up-to-date base reference. This includes committed branch changes and local edits and selects affected MVP suites. Unknown inputs and shared configuration retain conservative coverage. Report failures, unavailable prerequisites and relevant checks not run in the PR summary. Run the unfiltered `node tools/test.mjs` for full MVP verification before a macOS release or when broad verification is explicitly needed; neither command qualifies deferred platforms.
- Review diffs for personal data, secrets, non-English content, broken links, and third-party notices before committing.
- Do not select or change the project's license, remove required attribution, or publish remotely without explicit authorization.

### Decisions worth knowing

These are product boundaries and accepted architectural decisions, not claims that every safeguard or target platform is implemented and verified.

| Decision or title                                               | Practical consequence                                                                                                                                                                                                                                                      | Source                                                                                                                                                                                                                            |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Personal organizational core                                    | Tasks, knowledge and document management serve one person; email/calendar remain external. Do not introduce built-in shared-workspace semantics or mandate an organizational method.                                                                                       | [Foundations](requirements/data/foundations.md#personal-organizational-core)                                                                                                                                                      |
| GOAL-0004 — Delegate work while retaining decision authority    | Product actions execute within the user's request and configured access without per-action approval; internal changes remain reversible. Account authorization and destructive-content protections stay separate. An uncertain outcome is not proof that nothing happened. | [GOAL-0004](requirements/data/goals/GOAL-0004-decision-authority.md), [voice: errors and uncertainty](design/brand/docs/voice.md#errors-and-uncertainty)                                                                          |
| Plugin trust and synchronization ownership                      | Plugins are trusted code, not sandboxed adversaries. Use core versioned writes; synchronization plugins supply transport, not independent history or recovery rules.                                                                                                       | [Foundations](requirements/data/foundations.md#plugin-trust-and-synchronization-ownership)                                                                                                                                        |
| Application-bound execution                                     | Hiding a view does not stop its work; workspace closure and application quit do. Reopening retained conversations waits for user interaction, rather than silently replaying interrupted work.                                                                             | [Application and agent strategy](docs/architecture/04-solution-strategy/application-and-agent.adoc)                                                                                                                               |
| Hosting and data processing                                     | Official synchronization must prevent operator decryption; authorized plaintext AI processing is a separate flow. User-provided AI credentials and operational settings stay device-local and are not transferred with workspaces.                                         | [Foundations](requirements/data/foundations.md#hosting-and-data-processing)                                                                                                                                                       |
| ADR-0001 — Coordinate named tab layouts and per-pane navigation | Keep layout, pane history and presentation separate from domain state and execution; built-ins, plugins and agents use semantic host navigation.                                                                                                                           | [Accepted ADR-0001](docs/architecture/09-architecture-decisions/ADR-0001-ui-orchestration.adoc)                                                                                                                                   |
| ADR-0008 / ADR-0009 — Diagnostics and workspace identity        | Use bounded, non-blocking, device-local diagnostics outside workspace history/sync. ADR-0009 replaces user identity with portable workspace correlation; shared IDs never grant shared runtime state or access.                                                            | [ADR-0008](docs/architecture/09-architecture-decisions/ADR-0008-device-local-diagnostics.adoc), [superseding identity decision ADR-0009](docs/architecture/09-architecture-decisions/ADR-0009-workspace-diagnostic-identity.adoc) |
| ADR-0010 — Derive file references from Git-owned change history | Git is the durable authority; reference projections must be reconstructible. Do not automatically finish or roll back interrupted file operations, or guess a target from a reused path.                                                                                   | [Accepted ADR-0010](docs/architecture/09-architecture-decisions/ADR-0010-git-authoritative-file-history.adoc)                                                                                                                     |
