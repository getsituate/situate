# UI component inventory

## Libraries and ownership

| Consumer                                       | Public entry point                                    | Component source                                                     |
| ---------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------- |
| Design workshop, including its controls window | `client/workshop/src/ui/index.ts`                     | `client/workshop/src/ui/`                                            |
| Production client                              | `@situate/ui`                                         | `client/packages/ui/src/`                                            |
| Plugin views                                   | Intended to use the production library under REQ-0026 | Runtime delivery belongs to the plugin integration, not the workshop |

The libraries are independent. Matching filenames and small Vue props/events/slots make selected components portable; they do not require matching designs or automatic synchronization. The workshop catalog renders every component exported by its own library. Feature views remain reachable through their existing scenarios.

`plain` is an explicit escape hatch for specialized controls such as file trees, pane tabs, editor surfaces and chat composers. Those controls retain their interaction-specific geometry. ## Coverage and remaining candidates

The general library covers the recurring controls needed by current workspace, chat, file, document, provider, settings and plugin examples. Field associations, empty states and notices cover common composition needs without embedding workspace models, service calls or product text in the library.

The following patterns still contain feature-specific behavior. Extract a shared component when its contract can be demonstrated in more than one real flow; a matching silhouette alone is not enough.

- **Menus and anchored popovers:** shared Menu and Popover own surface positioning, dismissal and focus. Feature callers retain actions, selected values and domain state. Select keeps its separate listbox/sheet contract; a value picker is not an action menu.
- **Tabs, pane histories and trees:** identity, navigation, drag/drop, selection and resource lifetime remain in their feature models. The present Button and IconButton primitives standardize controls, not those domain semantics.
- **Progress and loading:** Progress supports measured and indeterminate values. Form waiting feedback reuses it while retaining its existing pausable visual estimate and Mini Bend. Step navigation and expressive illustration timelines remain separate; neither represents measured operation completion. A skeleton remains a candidate only for a stable loading layout.
- **Structured collections:** cards, rows, document grids and tag choices remain compositions. Table sorting, virtualization and multi-selection need concrete data and interaction contracts before becoming general widgets.
- **Date/time picking, rich text and file upload:** no general public component is supplied. Native input types remain available; specialized authoring and transfer workflows need separate designs and platform checks. The client's hidden attachment file picker remains native rather than being modeled as a text field.
- **Scrollbars and ResizeHandle:** both libraries provide native-scroll indicators and bounded pixel resizing. Pane geometry and persistence remain caller-owned.

Switches, removable document filters, expandable sections and action-menu surfaces use the shared workshop components. IconButton and title-bearing Button supply Tooltip centrally; native title attributes on passive filenames and paths remain text-overflow hints, not interactive help. Informational badges, attachment-removal actions and actual checkboxes retain their distinct semantics.

Plugin host integration and platform-specific behavior follow [REQ-0026](../../../../requirements/data/requirements/REQ-0026-provide-plugin-defined-views.md) independently of component availability.

## Design basis

The [brand handbook](../../../../design/brand/README.md) governs paper/surface backgrounds, plum text, rounded geometry and restrained daily-work feedback. Shared controls inherit the current workspace accent rather than introducing another palette. Menus organize actions; disclosures reveal content; switches apply settings; chips remove filters. Similar appearance does not make these behaviors interchangeable.

Supporting guidance: UI Skills on [design-system evolution](https://www.ui-skills.com/skills/kemiljk/design-system-evolution/llms.txt), [accessibility](https://www.ui-skills.com/skills/ibelick/fixing-accessibility/llms.txt) and [UI polish](https://www.ui-skills.com/skills/jakubkrehel/better-ui/llms.txt). Situate's tokens, motion and Vue conventions take precedence over external recipes.

## Manual adoption

1. Choose a component and its states in **Component library**, then inspect its uses in the relevant feature scenario.
2. Review the matching destination component and public contract. Preserve existing callers or migrate them explicitly.
3. Copy the selected Vue file, relative helpers/styles and appropriate tests into `client/packages/ui/src/`; update that library's exports. Text controls also use `text-control.ts` and `text-control.css`. Select, Scrollbars and ResizeHandle have their own local dependencies.
4. Reconcile token values and caller-supplied localization. Do not copy synthetic services or connect product imports to workshop files.
5. Run production component, flow, browser and visual checks. Browser geometry does not establish native-device or assistive-technology behavior.

Simple self-contained components can be copied unchanged. Components with helpers need a small group of files; feature views also need real state/service integration. A later workshop change has no effect on the copied product version.
